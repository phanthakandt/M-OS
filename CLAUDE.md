# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A point-and-click desktop-simulator horror game built in Godot 4.6 (GL Compatibility renderer). The player interacts entirely through a fake retro OS UI (windows, a taskbar, a Files app, a "DevCrack" unpack/repack tool) — no 3D, no physics. This repo currently holds an early MVP slice: boot into a desktop, read a rules note, and use DevCrack — a general-purpose tool available on any file — to disable each file's `data.protected` archive entry and unlock its contents.

## Running the project

There is no CLI build, lint, or test tooling in this repo — GDScript projects don't have one by default and none has been added here. Development happens in the Godot editor:

- Open `project.godot` in **Godot 4.6**, then run `scenes/Main.tscn` (F5) — it's already set as `run/main_scene`.
- New or changed asset files (fonts, `.tres`, scenes) are only auto-imported when the Godot editor regains OS focus or you trigger it manually (FileSystem dock → right-click → Reimport). If you edit project files from outside the editor (e.g. a headless agent), the editor won't pick them up until it's focused again — don't assume a change is live just because the file was saved.
- Do not launch a second Godot process against this project directory while the editor already has it open — both processes writing to `.godot/` concurrently can corrupt the import cache.

## Architecture

### Display settings (`project.godot`)

Base resolution is 384×216, window override 1536×864 (exact ×4). `window/stretch/mode` is set to `"canvas_items"` — layout code still thinks in the small 384×216 coordinate space, but Godot draws text and UI chrome natively at full window resolution rather than rendering small and upscaling the whole frame. This was deliberately changed from the initial `"viewport"` mode because that mode bakes the whole scene into a tiny raster image before scaling it up, which blurs text; don't switch back without knowing that tradeoff. `textures/canvas_textures/default_texture_filter` is Nearest, which matters once actual pixel-art sprite textures are added — right now the whole UI is `StyleBoxFlat` fills plus text, no image sprites, so it's currently inert.

Gotcha: built-in Godot controls that draw their own theme icon (e.g. `CheckBox`'s check glyph) size that icon in fixed absolute units of this same 384×216 coordinate space, completely independent of any `font_size`/`custom_minimum_size` override — on this tiny canvas that icon reads as oversized next to the pixel fonts, and there's no cheap per-node fix short of overriding the theme icon itself. Prefer a plain toggle `Button` with a bracket-style text prefix instead (see `FilesApp`'s hidden-file toggle) — it stays entirely font-driven like everything else in the UI.

### Autoloads

- **`Palette`** (`scripts/autoload/palette.gd`) is the single source of truth for the color palette (including one-off colors like `SCRIM` and `VOID` — even a plain color used once, e.g. a modal's scrim or a blackout overlay, should be a named `Palette` constant, not an inline `Color(...)`) and for `StyleBoxFlat` construction (`window_style()`, `titlebar_style(active)`, `task_item_style()`, `blob_marked_style()`, etc.), plus the two pixel fonts (`font_body` = VT323, `font_chrome` = Press Start 2P). Never hardcode a color or build a `StyleBoxFlat` elsewhere — call a `Palette` builder/constant from a node's `_ready()` and apply it via `add_theme_*_override`.
- **`GameState`** (`scripts/autoload/game_state.gd`) holds per-file runtime progress: `unlocked_files` (keyed by `FileData.id`/`resource_path`) via `is_unlocked(file)`/`mark_unlocked(file)` (a dormant override path — nothing currently calls `mark_unlocked`), and `_disabled_archive_entries` (keyed by file, then by `BlobData.id`) via `is_archive_entry_disabled(file, entry_id)`/`set_archive_entry_disabled(file, entry_id, disabled)`, which `DevCrackApp` uses for its unpack puzzle (see below). `get_lock_reason(file) -> LockReason` (`enum { UNLOCKED, PROTECTED, CORRUPTED }`) computes live *why* a file is locked, not just whether: `PROTECTED` means a `should_remove` entry (e.g. `data.protected`) is still enabled — the intended puzzle state; `CORRUPTED` means a non-`should_remove` entry (essential data) has been disabled instead — a self-inflicted break. `is_locked(file)` is just `get_lock_reason(file) != LockReason.UNLOCKED`. Neither reads a one-way flag — both conditions are fully reversible by re-enabling the relevant entry — and `reset_progress()` clears everything. It also holds the runtime "trash": `delete_file(file)`/`delete_folder(folder)` record an entry (keyed the same way, folders by `resource_path` since `FolderData` has no `id` field) and emit `trashed_changed`. Both check `can_delete_file(file)`/`can_delete_folder(folder)` — i.e. `not file.is_protected`/`not folder.is_protected` — first and return `false` (a no-op) if the entry is protected, but callers are expected to gate at the UI level instead of relying on that return value: `FilesApp` only offers a "Delete" context-menu item when `can_delete_*` is true in the first place (see below), so a protected entry's row never shows an option that would just fail. `is_file_deleted(file)`/`is_folder_deleted(folder)` gate what `FilesApp` renders, and `get_trashed_files()`/`get_trashed_folders()` feed `TrashApp`. Deleting a folder trashes it as one entry — its contents are never individually walked or trashed — and, like everything else here, this never mutates the `FolderData`/`FileData` resource itself. The "readme.txt" desktop icon is a file conceptually but isn't backed by a `FileData` resource, so it gets its own flag/methods instead of an entry in the dictionaries above: `is_readme_deleted()`/`delete_readme()` (also emits `trashed_changed`; unlike `delete_file`/`delete_folder` there's currently no protected/undeletable variant of this one).

### Window system (`scripts/window/`, `scenes/window/Window.tscn`)

`AppWindow` (`window.gd`) is the reusable chrome (Panel + TitleBar + ContentSlot), tracking `window_id`/`window_title` (both set by `setup(title, id)`) and emitting `closed(window_id)` / `focused(window_id)`. `WindowManager` (`window_manager.gd`) is a plain `Node` — one lives under each `Desktop`, it is not an autoload — exposing:

- `open_window(content: Control, title: String, rect: Rect2) -> AppWindow` — callers instantiate their own app scene, then hand it to `open_window`, which reparents it into the new window's `ContentSlot` and handles focus/z-order/taskbar sync.
- `focus_window(window_id)` — **toggles**: if the window is already the active, visible one, it hides (minimizes) instead of re-focusing. This is the taskbar button's intentional click-to-minimize behavior (`Desktop._on_window_opened`) and should not be reused elsewhere.
- `reveal_window(window_id)` — show + focus only, no minimize branch. Use this for every "open/bring to front" action (desktop icons, start menu, reopening an already-open file/singleton window) — `Desktop._focus_if_open`, `FilesApp._open_file`, and `TaskManagerApp` all call this, never `focus_window`.
- `get_open_windows() -> Array` — snapshot of `{id, title, visible}` per open window, used by `TaskManagerApp` to render its process list.
- `close_window(window_id)` — closes a window the same way its own titlebar close button does (emits `closed`, then `queue_free`s it); no-ops if the id is unknown.

When the closed window was the active one, `_on_window_closed` calls `_focus_topmost_visible()` to bring the next topmost *visible* window forward automatically (minimized ones are skipped, and if nothing visible is left `_active_id` just stays `""` — no window ends up stuck unfocused until the player clicks something). "Topmost" is read from `window_layer`'s actual child order (last child = topmost, the same convention `_focus()` itself maintains via `move_child`), not `_windows` dictionary order — the dictionary preserves insertion order, which drifts from z-order the moment any window is refocused, so it can't be used to answer "what's on top" reliably.

Apps never touch `AppWindow` directly, only this API plus their own signals.

### Data-driven content (`scripts/resources/`, `data/`)

`FileData`, `FolderData`, `RuleData`, `BlobData` are `Resource` subclasses (declared with `class_name`, no autoload needed) saved as `.tres` files under `data/files/` and `data/rules/`, plus the file/folder tree root `data/drive.tres`. Puzzle content (rule text, file metadata, which blob is correct to remove) lives entirely in these `.tres` files, not in scripts.

Resource immutability rule: preloaded/loaded `Resource` instances (including everything under `data/`) are cached singletons for the process's lifetime — **never mutate a `Resource` field at runtime** (e.g. `FileData`/`FolderData.is_protected`) — it's read-only initial data. `FileData` has no `is_locked` field at all: whether a file is locked, and why, is derived entirely from its `blobs` and computed live by `GameState.get_lock_reason(file)` — a `should_remove` blob still enabled is `PROTECTED`, any blob disabled that *isn't* `should_remove` is `CORRUPTED` (this doesn't require a `should_remove` blob to exist at all — disabling essential data breaks a file regardless of whether it has a "protection" blob too, see below). All runtime/session progress (unlocked, disabled archive entries, trashed) lives in the `GameState` autoload instead, keyed off `FileData.id`, and callers compute effective state via `GameState.is_locked(file)` / `GameState.can_delete_file(file)` rather than reading mutated resource fields. File-browser navigation state (history, current folder, show-hidden) similarly lives entirely in `FilesApp`, never on `FolderData`/`FileData`. `is_protected` is currently set on two entries in `data/drive.tres` — the "user" and "system" subfolders — mark any other file/folder undeletable the same way, directly in its `.tres`. `GameState._folder_key()` falls back to `FolderData.resource_path` for folders (unlike files, which have an explicit `id`). This has only ever been exercised by user/system, both `is_protected` (so `delete_folder` is never actually called on them). Before adding the first deletable folder, verify sibling sub-resources embedded in the same `.tres` get distinct `resource_path` values — if not, give `FolderData` an explicit `id` field like `FileData` already has.

### Apps (`scripts/apps/`, `scenes/apps/`)

Each app (`NoteViewer`, `FilesApp`, `DevCrackApp`, `TaskManagerApp`, `TrashApp`) is a standalone `Control` scene, instantiated by whoever wants to open it (`Desktop`, or another app) and handed to `WindowManager.open_window`. Only call an app's configuration methods (e.g. `unpack(file)`, `show_plain(text)`, `TaskManagerApp.self_window_id = ...` / `.refresh_list()`) **after** `open_window` has added it to the tree — its `@onready` references aren't valid before that.

`FilesApp` is a full file browser over the `FolderData`/`FileData` tree rooted at `data/drive.tres`. Back/forward navigation, the current path, and the hidden-files toggle are all plain state on the `FilesApp` instance (`_history`, `_history_index`, `_show_hidden`) — never on the resources themselves, per the immutability rule above. Entering a new folder truncates any forward history, like a browser. Folders sort before files, hidden entries (`is_hidden`) are omitted unless the toggle is on, locked files are shown (row text gets a `(locked)` suffix) but `_open_file` refuses to open one directly — see below — and trashed files/folders (`GameState.is_file_deleted`/`is_folder_deleted`) are omitted entirely. Double-clicking a file that already has an open `NoteViewer` window calls `WindowManager.reveal_window` instead of opening a duplicate (`_open_file_windows`, keyed by `FileData.id`); a second, separate `_devcrack_windows` map does the same for DevCrack windows, since a file can have both a `NoteViewer` and a `DevCrackApp` window open on it at once. `Desktop` does the same single-instance pattern for the apps it launches itself (drive icon, README, SYSTEM.LOG, task manager, trash) via its own `_singleton_windows` map keyed by an arbitrary app key (see `_focus_if_open`).

Right-clicking a file row opens a `ContextMenu` (see below) with "Open" (same effect as double-click — `_open_file`), "Unpack through DevCrack" (`_open_devcrack`, always offered, on every file regardless of extension), and "Delete" (`GameState.delete_file`, then `_close_all_windows_for(file)`) *only if* `GameState.can_delete_file` is true — protected files just don't get a "Delete" item at all, same pattern as desktop icons with no `delete_action` (see `DesktopIconUI`/`Desktop._wire_icon` below). Folder rows get the same "Open"/"Delete" pair (via `GameState.can_delete_folder`) but no unpack option — DevCrack only ever operates on files; deleting a folder recurses `_close_open_windows_under(folder)`, which calls `_close_all_windows_for` per file so nothing dangles either level down. `_close_all_windows_for(file)` is the one place that knows a file can have both an `_open_file_windows` (`NoteViewer`) and a `_devcrack_windows` (`DevCrackApp`) entry open at once and closes whichever exist — deleting a file used to only check the former, leaving a stray DevCrack window behind. Which target the menu acts on is tracked in `_context_target_file`/`_context_target_folder` (exactly one set at a time) rather than rebinding the shared menu's signal per row. `_open_file` now refuses any `GameState.is_locked(file)` file — not just `.mos` ones — via `warning_dialog.show_message(...)` instead of opening a window (see `WarningDialog` below), branching on `GameState.get_lock_reason(file)` for the wording: `CORRUPTED` gets "ไม่สามารถเปิดไฟล์นี้ได้เนื่องจากไฟล์เสียหาย" (this much *is* realistic OS-style error differentiation — corrupted vs. merely access-denied is a distinction a real file system would surface), everything else (`PROTECTED`) gets the plain "ไม่สามารถเปิดไฟล์นี้ได้". Neither message points the player at DevCrack, names an entry, or explains *how* to fix it — that stops-short-of-a-walkthrough line is the deliberate house rule here (see `DevCrackApp` below for the same principle applied to REPACK's feedback, which stays silent even for `CORRUPTED`). `_open_devcrack` opens/reveals a `DevCrackApp` window the same way `_open_file` does for `NoteViewer`, and additionally connects to that `DevCrackApp` instance's `file_repacked` signal — a repack changes `GameState`'s archive-entry-disabled state, which nothing else tells `FilesApp` about (there's no dedicated signal for it the way `trashed_changed` covers deletes), so `_on_file_repacked` just calls `_rebuild_list()` to pick up the file row's now-current `(locked)` suffix. This connection is made fresh per `DevCrackApp` instance (never reused, unlike the shared dialogs), so no duplicate-connection guard is needed.

`DevCrackApp.unpack(file)` is reachable from any file via "Unpack through DevCrack" — no extension filtering, the engine doesn't interpret filenames specially — and **is never itself gated by lock state**: `FilesApp` calls it unconditionally, with no equivalent of the `is_locked` check `_open_file` does. This is deliberate, not an oversight — DevCrack is the *tool* that acts on a file's lock state, so gating entry into it on that same lock state would be circular (there used to be a `has_learned_devcrack` flag gating unpack on any locked file until the player had first repacked a non-locked one — but every puzzle file is locked now, so that flag could never be set on a fresh game and every file would permanently soft-lock; it's been removed along with the "gate" state/`GateLabel` it drove). It renders one row per `BlobData` "archive entry" on the file (all of them, always — entries are never removed from the list, see below) — each entry has its own `filename`/`extension` (e.g. `a1.data`, falling back to `label` alone if `filename` is empty, for older content like `meta_tag`'s blob that predates those fields) and, on the right of the row, either its `last_modified` flavor string or the word "offline" if the entry is currently disabled. No row styling may hint which entries are `should_remove` before the player has touched them — every row looks identical, aside from that flavor text, until the player's own toggling changes it — which is also why DevCrack carries no in-app hint text at all (`FileData` has no `reveals_clue`-style field; the puzzle is trial-and-error only). Right-clicking a row opens the app's own `ContextMenu` instance with "Copy"/"Paste"/"Disable" (or "Enable", labeled dynamically from current state) — same right-click-not-always-visible-buttons convention as `FilesApp` — tracked via a single `_context_target_blob` (only one target type here, unlike `FilesApp`'s file/folder pair). Copy/Paste are still stubs; selecting either just calls `warning_dialog.show_message("ยังไม่รองรับฟังก์ชันนี้")` (see `WarningDialog` below) instead of doing anything. The toggle action calls `GameState.set_archive_entry_disabled(file, blob.id, ...)`, flips the row to 50% opacity + "offline" (`row.modulate.a`, no new `Palette` color needed), and — critically — **is reversible in both directions**: re-enabling a `should_remove` entry re-`PROTECTED`-locks the file, and *disabling* a non-`should_remove` entry (essential data, not the intended block) locks it too, as `CORRUPTED` — the player broke the archive by removing something that wasn't meant to go. Both conditions clear the moment the relevant entry is toggled back, since `GameState.get_lock_reason(file)` is computed live from current disabled-state on every call, not cached from a one-time "repack succeeded" flag (there's no `repacked_files`/`is_repacked`/`mark_repacked` anymore). Row styling never distinguishes `should_remove` from non-`should_remove` entries — same "no advance hints" rule as before — so `CORRUPTED` is never discoverable from the row list itself or from REPACK's feedback (see below); the only place it surfaces at all is `FilesApp`/`Desktop._open_readme`'s open-attempt message, which says "ไฟล์เสียหาย" ("file corrupted") — realistic OS-style error differentiation, not a puzzle hint, since it still never says *which* entry or *how* to fix it. By convention every file's `should_remove` entry is named `data.protected` (both `def_mos.tres` and `forbidden_file.tres` set it that way — that blob is what makes the file `PROTECTED`-lockable specifically; `CORRUPTED` needs no `should_remove` blob at all, see above) so the player learns to recognize what to look for. `REPACK` (bottom-right, via `BottomBar`'s `alignment = ALIGNMENT_END` with the `Scroll` above it eating all flexible height) is **never gated** either — the player can press it anytime regardless of current entry state, there's no pass/fail validation blocking the click itself. `_on_repack_pressed` does not branch on outcome at all — it emits `file_repacked(current_file, unlocked)` (still computed from `GameState.get_lock_reason(current_file)`, for any future listener that cares), then unconditionally pops `warning_dialog.show_message("repack เสร็จสิ้น")` and closes its own window via `window_manager.close_window(self_window_id)` (both `window_manager` and `self_window_id` are set by `FilesApp._open_devcrack` the same way `TaskManagerApp.self_window_id` is set by `Desktop` — `window_manager` before `open_window`, `self_window_id` from the returned `AppWindow` after). This is deliberate: a real repack tool performs the operation and reports "done," it doesn't sit there judging whether the result happens to be openable — that's what `FilesApp`'s own lock check is for, discovered separately the next time the player tries to open the file. There is no `feedback_label` anymore (removed along with the branching) — every repack looks identical from the player's side regardless of `PROTECTED`/`CORRUPTED`/`UNLOCKED`. Same "no naming a specific entry, no explaining the cause, no suggesting a next step" house rule as `FilesApp._open_file`'s messages — those *do* now distinguish `CORRUPTED` from `PROTECTED` in wording (see above), but REPACK stays silent regardless: puzzle knowledge is game content the player has to work out, not something the tool's own UI leaks.

`TaskManagerApp` (`task_manager_app.gd`) lists every open window as a process row (name button + `[x]` close button), driven entirely by `WindowManager.get_open_windows()`. It re-subscribes to `window_opened`/`window_closed` to rebuild the list live, and takes a `self_window_id` (set by `Desktop._open_task_manager` right after `open_window` returns, followed by an explicit `refresh_list()` call) so it can filter its own row out — it can't rely on the window-opened signal alone, since that fires for it before `self_window_id` is assigned.

`TrashApp` (`trash_app.gd`) lists everything `GameState` has trashed (folders first, then files, `readme.txt` last among file-likes), rebuilt on `GameState.trashed_changed`. Each row has a `[restore]` button bound to `GameState.restore_file`/`restore_folder`/`restore_readme` via a `Callable.bind()` per row — restoring a file/folder just erases its trashed-dictionary entry and re-emits `trashed_changed`; `FilesApp` picks the change up automatically on its next `_rebuild_list()` since it already checks `GameState.is_file_deleted()`/`is_folder_deleted()` every time, so no change to `FilesApp` was needed. Restore has no protected/undeletable equivalent — anything that was successfully trashed can always be restored.

### UI components (`scripts/ui/`, `scenes/ui/`)

`ConfirmDialog` (`confirm_dialog.gd`) is a reusable modal: scrim (`Palette.SCRIM`) + `window_style` `PanelContainer` with a message label and `[ ยืนยัน ]` (`blob_marked_style`) / `[ ยกเลิก ]` (`task_item_style`) buttons. Call `ask(message: String)` to show it; it emits `confirmed` or `cancelled` (clicking the scrim outside the panel also cancels). One instance lives on `Desktop` (`_confirm_dialog`, added after the start-menu layer so it renders on top of everything) and is reused across callers — since it's shared, always connect to `confirmed` with `CONNECT_ONE_SHOT` and guard against double-connecting if the same flow can be triggered again before the dialog resolves (see `Desktop._confirm_shutdown`).

`WarningDialog` (`warning_dialog.gd`) is `ConfirmDialog`'s single-button sibling, for messages the player just needs to acknowledge rather than decide on — same scrim + `window_style` `PanelContainer` structure, but only a `[ OK ]` button and only one signal, `acknowledged` (no `cancelled` — there's no second path out). Unlike `ConfirmDialog`, **clicking the scrim does not close it**: the scrim's `mouse_filter = STOP` (set in the `.tscn`) still blocks clicks from passing through to whatever's behind it, but nothing is connected to its `gui_input`, so the only way out is the OK button. Call `show_message(message: String)`. It's instantiated once on `Desktop` (`_warning_dialog`, same pattern as `_confirm_dialog`) but apps that need it don't reach through `Desktop` to find it — it's handed down as a plain `warning_dialog` property, set by whoever opens the app *before* calling `open_window` (same convention as `window_manager`): `Desktop._open_files_app` sets `FilesApp.warning_dialog`, and `FilesApp._open_devcrack` forwards its own `warning_dialog` to the `DevCrackApp` it opens, since `DevCrackApp` is never instantiated directly by `Desktop`. Both apps guard every call with `if warning_dialog:` before using it, the same null-check convention already used for `window_manager`. This replaced an earlier per-app `_show_notice()` (a transient auto-hiding label with a timer) in both `FilesApp` and `DevCrackApp` — that method and its `_notice_label` var are gone from both.

`ContextMenu` (`context_menu.gd`) is a reusable right-click menu: an invisible full-rect `Catcher` (click-outside-to-close, no dimming — unlike `ConfirmDialog` this isn't a modal) plus a `window_style` `PanelContainer` of buttons. Call `open_at(global_pos: Vector2, items: Array)` with `items` as `[{"label": ..., "action": ...}]`; it emits `item_selected(action: String)` and clamps the panel's position so it never renders outside its own rect. Each button gets `custom_minimum_size.x = MIN_ITEM_WIDTH` so the menu reads as a consistent width regardless of how many items or how short their labels are ("Open" alone shouldn't look narrower than "Open"/"Delete" together) — height is left to shrink-to-content via `panel.reset_size()`, so a single-item menu is exactly one row tall. Each surface that needs one owns a single instance covering that surface's own rect — `FilesApp` (file/folder rows), `Desktop` (desktop icons), and `DevCrackApp` (archive-entry rows) each have their own — and, since that one instance is reused for every row/icon on the surface, the caller tracks "what am I acting on" itself (e.g. `FilesApp._context_target_file`/`_context_target_folder`, `Desktop._context_target_open_action`/`_context_target_delete_action`, `DevCrackApp._context_target_blob`) rather than rebinding `item_selected` per open.

### Desktop shell (`scripts/desktop/`, `scenes/desktop/Desktop.tscn`)

`Desktop` (`desktop.gd`) wires everything together: owns the `WindowManager`, builds taskbar entries from `WindowManager`'s `window_opened`/`window_closed` signals, and builds a start menu (scrim + `PanelContainer`, opened by left-clicking the `start_button`/"M-OS" taskbar button; entries are data in `_start_menu_items`, so adding one is just appending a `{"label": ..., "action": Callable}` before `_build_start_menu()` runs). Current entries: my drive, trash, system log, task manager, restart, logout, shutdown. `restart`/`logout` both just call `GameState.reset_progress()` then `get_tree().reload_current_scene()` — the duplication is intentional (they read differently to the player but there's currently no state that needs to diverge between them); don't merge them into one function. `shutdown` goes through `ConfirmDialog` (`_confirm_shutdown` → `_do_shutdown`, which shows a black `Palette.VOID` overlay with a "process terminated" message before `get_tree().quit()`).

`DesktopIconUI` (`desktop_icon.gd`) is a generic icon: double-click emits `activated`, right-click emits `context_requested` (both gated to their respective mouse button — `MOUSE_BUTTON_LEFT`/`MOUSE_BUTTON_RIGHT` — so a right-click double-click doesn't also fire `activated`). **Configure it via `configure(glyph, label_text)`, never by assigning the `.glyph`/`.label_text` export vars directly** — Godot runs a child's `_ready()` before its parent's, so by the time `Desktop._ready()` would assign those properties, the icon has already copied its (empty-string default) export values into its labels; the assignment is silently too late. `Desktop._wire_icon(icon, glyph, label, open_action, delete_action = Callable(), unpack_action = Callable())` is the one place that connects both signals: `activated` goes straight to `open_action`, and `context_requested` opens `Desktop`'s shared `ContextMenu` with "Open" plus "Unpack through DevCrack"/"Delete" only if the matching action was passed and is valid — drive/trash are apps with no `FileData`/`FolderData` behind them so they're called with neither and get "Open" only. Icons live in one of two plain `VBoxContainer`s directly on `Desktop.tscn`: `IconGrid` (top-left — drive, trash) and `TopRightIconGrid` (top-right — readme.txt only, currently); there's nothing dynamic about the split, it's just two fixed-offset containers a new icon gets placed into by hand depending on where it should sit.

readme.txt is the one icon that represents an actual file rather than an app, and unlike everything else on the desktop it's backed by a real `FileData` — `Desktop.README_FILE` (`data/files/readme.tres`) — rather than being a hardcoded special case, specifically so it can go through the exact same "any file can be unpacked" path as a `FilesApp` row: `_wire_icon` passes it `_delete_readme` (calls `GameState.delete_readme()` and hides the icon — this part is still readme-specific, not `GameState.delete_file`, since it isn't part of the browsable `data/drive.tres` tree) and `_open_readme_devcrack` (mirrors `FilesApp._open_devcrack` — instantiates `DevCrackApp`, wires `warning_dialog`/`window_manager`/`self_window_id`, calls `.unpack(README_FILE)` — just opened from a desktop icon instead of a file-browser row, tracked under `_singleton_windows["readme_devcrack"]` alongside the existing `"readme"` key for its `NoteViewer` window, the same dual-window split `FilesApp` does with `_open_file_windows`/`_devcrack_windows`). `_open_readme` itself now gates on `GameState.get_lock_reason(README_FILE)` first, branching the warning message the same way `FilesApp._open_file` does — `README_FILE` currently carries no `should_remove` blob (just one flavor blob, `readme_meta`, for a non-empty DevCrack view), so it can never go `PROTECTED`, but it *can* still go `CORRUPTED`: disabling `readme_meta` (the only blob it has) breaks it exactly like disabling essential data on any other file, and the open-attempt will say so (`CORRUPTED`'s "ไฟล์เสียหาย" message). It is **not** opened automatically at boot anymore, the player must open the icon, and stays hidden across a scene reload if already deleted — see `GameState.is_readme_deleted()` check in `Desktop._ready()`. Current icons: "drive" (`FilesApp` on `data/drive.tres`), "readme.txt" (as above), and "trash" (`TrashApp`).
