# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A point-and-click desktop-simulator horror game built in Godot 4.6 (GL Compatibility renderer). The player interacts entirely through a fake retro OS UI (windows, a taskbar, a Files app, a "DevCrack" unpack/repack tool) — no 3D, no physics. This repo currently holds an early MVP slice: boot into a desktop, read a rules note, and use DevCrack — a general-purpose tool available on any file — to disable each file's `data.protected` archive entry and unlock its contents.

## Running the project

There is no CLI build, lint, or test tooling in this repo — GDScript projects don't have one by default and none has been added here. Development happens in the Godot editor:

- Open `project.godot` in **Godot 4.6**, then run `scenes/Main.tscn` (F5) — it's already set as `run/main_scene`.
- New or changed asset files (fonts, `.tres`, scenes) are only auto-imported when the Godot editor regains OS focus or you trigger it manually (FileSystem dock → right-click → Reimport). If you edit project files from outside the editor (e.g. a headless agent), the editor won't pick them up until it's focused again — don't assume a change is live just because the file was saved.
- Do not launch a second Godot process against this project directory while the editor already has it open — both processes writing to `.godot/` concurrently can corrupt the import cache.

## Architecture

### Display settings (`project.godot`)

Base resolution is 384×216, window override 1536×864 (exact ×4). `window/stretch/mode` is set to `"canvas_items"` — layout code still thinks in the small 384×216 coordinate space, but Godot draws text and UI chrome natively at full window resolution rather than rendering small and upscaling the whole frame. This was deliberately changed from the initial `"viewport"` mode because that mode bakes the whole scene into a tiny raster image before scaling it up, which blurs text; don't switch back without knowing that tradeoff. `textures/canvas_textures/default_texture_filter` is Nearest, which matters once actual pixel-art sprite textures are added — right now the whole UI is `StyleBoxFlat` fills plus text, no image sprites, so it's currently inert.

Gotcha: built-in Godot controls that draw their own theme icon (e.g. `CheckBox`'s check glyph) size that icon in fixed absolute units of this same 384×216 coordinate space, completely independent of any `font_size`/`custom_minimum_size` override — on this tiny canvas that icon reads as oversized next to the pixel fonts, and there's no cheap per-node fix short of overriding the theme icon itself. Prefer a plain toggle `Button` with a bracket-style text prefix instead (see `FilesApp`'s hidden-file toggle) — it stays entirely font-driven like everything else in the UI.

### Autoloads

- **`Palette`** (`scripts/autoload/palette.gd`) is the single source of truth for the color palette (including one-off colors like `SCRIM`, `VOID`, and `TRANSPARENT` — even a plain color used once, e.g. a modal's scrim or a blackout overlay, should be a named `Palette` constant, not an inline `Color(...)`) and for `StyleBoxFlat` construction (`window_style()`, `titlebar_style(active)`, `task_item_style()`, `task_item_style_invisible()`, `blob_marked_style()`, `chat_contact_row_style(selected, hovered)`, `chat_bubble_style(is_me)`, `start_menu_item_style(hovered)`, `sidebar_tab_style(selected, hovered)`, etc.), plus the two pixel fonts (`font_body` = VT323, `font_chrome` = Press Start 2P). Never hardcode a color or build a `StyleBoxFlat` elsewhere — call a `Palette` builder/constant from a node's `_ready()` and apply it via `add_theme_*_override`. `task_item_style_invisible()` is `task_item_style()`'s border width/content margin with fully transparent colors — for a row that should only show its box on hover, swap between the two rather than a bare `StyleBoxEmpty`, or the sudden border/margin appearing on hover will change the row's minimum size and jump the whole list (see `TaskManagerApp` below). Ghost-process corruption uses two color pairs, both driven by the same private `_corruption_t(ghost_count, max_count = 15) -> float` (`t = clamp(float(ghost_count) / float(max_count), 0.0, 1.0)`, then `t * t`) so the eased curve is only written once: `DESKTOP_BG_DANGER` is the endpoint for `Desktop.background` specifically — deliberately dark/desaturated (not bright/neon red) since it has to work as a full-screen background wash, unlike `ACCENT_WARN` which is sized for a small accent — and `desktop_corruption_color(ghost_count, max_count = 15) -> Color` lerps `DESKTOP_BG_1` toward it. `CANVAS_MODULATE_NORMAL`/`CANVAS_MODULATE_DANGER` are the endpoints for the *whole screen's* tint instead (identity `Color(1,1,1,1)` → `Color(1.0, 0.15, 0.2, 1)` — green/blue pulled down hard for a vivid, saturated red at full corruption rather than a muddy one; red left at 1.0 rather than boosted since a channel above 1.0 just clamps to a no-op on the Compatibility renderer's LDR backbuffer), and `corruption_modulate(ghost_count, max_count = 15) -> Color` lerps between them — see `Desktop`'s `CanvasModulate` node below for what actually consumes this. `_corruption_t` is quadratic (`t * t`) rather than linear, and deliberately eases *in* rather than out — the first several ghost processes should read as almost no change at all, only becoming obviously red as the count climbs toward `max_count`, so the corruption is meant to creep up unnoticed rather than announce itself the moment a `lived.process` spawns. Callers (currently just `Desktop`, see below) always go through `desktop_corruption_color()`/`corruption_modulate()` rather than repeating the lerp/clamp/ease themselves.
- **`GameState`** (`scripts/autoload/game_state.gd`) holds per-file runtime progress: `unlocked_files` (keyed by `FileData.id`/`resource_path`) via `is_unlocked(file)`/`mark_unlocked(file)` (a dormant override path — nothing currently calls `mark_unlocked`), and `_disabled_archive_entries` (keyed by file, then by `BlobData.id`) via `is_archive_entry_disabled(file, entry_id)`/`set_archive_entry_disabled(file, entry_id, disabled)`, which `DevCrackApp` uses for its unpack puzzle (see below). `get_lock_reason(file) -> LockReason` (`enum { UNLOCKED, PROTECTED, CORRUPTED }`) computes live *why* a file is locked, not just whether: `PROTECTED` means a `should_remove` entry (e.g. `data.protected`) is still enabled — the intended puzzle state; `CORRUPTED` means a non-`should_remove` entry (essential data) has been disabled instead — a self-inflicted break. `is_locked(file)` is just `get_lock_reason(file) != LockReason.UNLOCKED`. Neither reads a one-way flag — both conditions are fully reversible by re-enabling the relevant entry — and `reset_progress()` clears everything. It also holds the runtime "trash": `delete_file(file)`/`delete_folder(folder)` record an entry (keyed the same way, folders by `resource_path` since `FolderData` has no `id` field) and emit `trashed_changed`. Both check `can_delete_file(file)`/`can_delete_folder(folder)` — i.e. `not file.is_protected`/`not folder.is_protected` — first and return `false` (a no-op) if the entry is protected, but callers are expected to gate at the UI level instead of relying on that return value: `FilesApp` only offers a "Delete" context-menu item when `can_delete_*` is true in the first place (see below), so a protected entry's row never shows an option that would just fail. `is_file_deleted(file)`/`is_folder_deleted(folder)` gate what `FilesApp` renders, and `get_trashed_files()`/`get_trashed_folders()` feed `TrashApp`. Deleting a folder trashes it as one entry — its contents are never individually walked or trashed — and, like everything else here, this never mutates the `FolderData`/`FileData` resource itself. The "readme.txt" desktop icon is a file conceptually but isn't backed by a `FileData` resource, so it gets its own flag/methods instead of an entry in the dictionaries above: `is_readme_deleted()`/`delete_readme()` (also emits `trashed_changed`; unlike `delete_file`/`delete_folder` there's currently no protected/undeletable variant of this one). `_code_unlocked_apps` (keyed by an arbitrary `app_id` String, e.g. `"kikuchat"`) via `is_app_unlocked_by_code(app_id)`/`unlock_app_with_code(app_id)` is a **completely separate mechanic from everything above** — see `KikuChatApp` below for why this must never be conflated with the DevCrack/blob lock system. `GameState` doesn't know or compare any actual password here; it only remembers that a given app's code has been entered correctly once. Also cleared by `reset_progress()`. `_trashed_emails` (keyed directly by `EmailData.id`, no `_file_key`-style fallback since every email in `inbox.tres` always sets one) via `is_email_deleted(email)`/`delete_email(email)`/`restore_email(email)` is `MosMailApp`'s own trash — a separate dictionary/id-space from `_trashed_files`/`_trashed_folders` above, never shared, since `FileData` and `EmailData` ids aren't guaranteed unique against each other. Unlike files/folders there's no protected/undeletable concept for emails — any email, inbox or spam, can always be deleted into this one trash — and there's no dedicated signal either: `MosMailApp` just calls `_rebuild_email_list()` itself after every delete/restore, the same "no signal, caller rebuilds" pattern `FilesApp` already uses around `delete_file()`. Also cleared by `reset_progress()`.

`GameState` also owns the entire "ghost process" cascade — `TaskManagerApp`/`DevCrackApp` only call in and render, the same way `FilesApp` doesn't know DevCrack's blob probabilities. `_ghost_processes` (Array of `{id, name, hidden, killable}`, ids from an incrementing `_next_ghost_id`) plus signal `ghost_processes_changed` (same "shared dictionary + signal, subscriber rebuilds its list" pattern as `trashed_changed`) is session state like everything else here — cleared by `reset_progress()` — and is never capped, which is deliberate: an unkillable entry that lands is meant to sit there forever, accumulating pressure. `on_devcrack_repacked()` is called unconditionally by `DevCrackApp` on every REPACK press (any file, any outcome — REPACK never branches on outcome, see below) and has a flat 70% chance of spawning one `"lived.process"` entry (`hidden = false`, `killable = true`); it emits `ghost_processes_changed` only when that roll actually spawns something — a miss is a true no-op, so there's nothing for `Desktop`/`TaskManagerApp` to react to. `kill_ghost_process(id)` removes the matching entry and, **only if the entry that was just removed was named `"lived.process"`** (killing a `"ssecorp.devil"`, successfully or not, never cascades further), rolls a further 70% chance to spawn one `"ssecorp.devil"` entry (`hidden = true`, and only a 40% chance `killable = true` — i.e. `killable = randf() >= 0.6`); unlike `on_devcrack_repacked()`, it emits `ghost_processes_changed` unconditionally at the end regardless of whether a cascade spawn happened, since killing an entry is itself always a change. Both `Desktop`'s corruption tint and `TaskManagerApp`'s row list subscribe to `ghost_processes_changed`, so a spawn from REPACK and a kill (with or without cascade) both refresh the desktop background and the process list the same way — see `Desktop`/`TaskManagerApp` below. Both spawn paths go through one private `_spawn_ghost_process(name, hidden, killable)` helper so the id-assignment logic isn't duplicated. `get_ghost_processes()` returns `_ghost_processes` directly (read-only by convention) and `get_ghost_process_count()` is just its `.size()` — since killed entries are erased rather than flagged, the array's size already *is* "how many ghost processes are currently alive," no separate counter needed.

### Window system (`scripts/window/`, `scenes/window/Window.tscn`)

`AppWindow` (`window.gd`) is the reusable chrome (Panel + TitleBar + ContentSlot), tracking `window_id`/`window_title` (both set by `setup(title, id)`) and emitting `closed(window_id)`. It has no `focused` signal of its own — `_on_titlebar_gui_input` only initiates dragging, and `_input()` only handles the drag itself (mouse motion while `_dragging`, mouse-up to end it). Click-to-focus for the *whole* window is decided centrally by `WindowManager._input()` instead (see below), not per-window: an earlier version had each `AppWindow` check `Rect2(global_position, size).has_point(...)` on itself and emit its own `focused` signal, which fixed the original bug (only the titlebar could focus a window — `panel`/`content_slot`'s `gui_input` almost never fired, since `content_slot` is filled edge-to-edge by whatever app is loaded and that app's own interactive children consume the click first) but introduced a worse one: when two windows' rects overlapped at a click point, both could independently decide to focus themselves, and whichever's `_input()` happened to run last that frame — an ordering Godot doesn't guarantee matches visual stacking — won, occasionally focusing the window *behind* the one actually clicked. `WindowManager` (`window_manager.gd`) is a plain `Node` — one lives under each `Desktop`, it is not an autoload — exposing:

- `open_window(content: Control, title: String, rect: Rect2) -> AppWindow` — callers instantiate their own app scene, then hand it to `open_window`, which reparents it into the new window's `ContentSlot` and handles focus/z-order/taskbar sync.
- `focus_window(window_id)` — **toggles**: if the window is already the active, visible one, it hides (minimizes) instead of re-focusing. This is the taskbar button's intentional click-to-minimize behavior (`Desktop._on_window_opened`) and should not be reused elsewhere.
- `reveal_window(window_id)` — show + focus only, no minimize branch. Use this for every "open/bring to front" action (desktop icons, start menu, reopening an already-open file/singleton window) — `Desktop._focus_if_open`, `FilesApp._open_file`, and `TaskManagerApp` all call this, never `focus_window`.
- `get_open_windows() -> Array` — snapshot of `{id, title, visible}` per open window, used by `TaskManagerApp` to render its process list.
- `close_window(window_id)` — closes a window the same way its own titlebar close button does (emits `closed`, then `queue_free`s it); no-ops if the id is unknown.

When the closed window was the active one, `_on_window_closed` calls `_focus_topmost_visible()` to bring the next topmost *visible* window forward automatically (minimized ones are skipped, and if nothing visible is left `_active_id` just stays `""` — no window ends up stuck unfocused until the player clicks something). "Topmost" is read from `window_layer`'s actual child order (last child = topmost, the same convention `_focus()` itself maintains via `move_child`), not `_windows` dictionary order — the dictionary preserves insertion order, which drifts from z-order the moment any window is refocused, so it can't be used to answer "what's on top" reliably.

`WindowManager._input(event)` is what actually implements "click anywhere on a window focuses it": on every left mouse-button press it walks `window_layer`'s children topmost-first (same convention as `_focus_topmost_visible()`) and calls `_focus()` on the *first* visible window whose `Rect2(global_position, size)` contains the click — then returns immediately, never considering windows further down. Doing this centrally, in one place that already owns the z-order, rather than having each `AppWindow` independently check its own rect and self-report via a signal, is deliberate: a decentralized version is what originally caused clicking a window that's *behind* another one at that exact point to sometimes win focus instead of the one actually on top, since Godot doesn't guarantee sibling `_input()` call order matches visual stacking. Centralizing it removes that ambiguity — the loop itself defines the priority. It never calls `get_viewport().set_input_as_handled()`, so this is purely an observer — the same click still continues on to Godot's normal GUI dispatch afterward and reaches whatever `Control` inside the window (a button, a list row) would have handled it anyway; raising the window and clicking something inside it happen from the same single click.

Apps never touch `AppWindow` directly, only this API plus their own signals.

### Data-driven content (`scripts/resources/`, `data/`)

`FileData`, `FolderData`, `BlobData` are `Resource` subclasses (declared with `class_name`, no autoload needed) saved as `.tres` files under `data/files/`, plus the file/folder tree root `data/drive.tres`. Puzzle content (rule text baked into a file's own `content`, file metadata, which blob is correct to remove) lives entirely in these `.tres` files, not in scripts.

Resource immutability rule: preloaded/loaded `Resource` instances (including everything under `data/`) are cached singletons for the process's lifetime — **never mutate a `Resource` field at runtime** (e.g. `FileData`/`FolderData.is_protected`) — it's read-only initial data. `FileData` has no `is_locked` field at all: whether a file is locked, and why, is derived entirely from its `blobs` and computed live by `GameState.get_lock_reason(file)` — a `should_remove` blob still enabled is `PROTECTED`, any blob disabled that *isn't* `should_remove` is `CORRUPTED` (this doesn't require a `should_remove` blob to exist at all — disabling essential data breaks a file regardless of whether it has a "protection" blob too, see below). All runtime/session progress (unlocked, disabled archive entries, trashed) lives in the `GameState` autoload instead, keyed off `FileData.id`, and callers compute effective state via `GameState.is_locked(file)` / `GameState.can_delete_file(file)` rather than reading mutated resource fields. File-browser navigation state (history, current folder, show-hidden) similarly lives entirely in `FilesApp`, never on `FolderData`/`FileData`. `is_protected` is currently set on two entries in `data/drive.tres` — the "user" and "system" subfolders — mark any other file/folder undeletable the same way, directly in its `.tres`. `GameState._folder_key()` falls back to `FolderData.resource_path` for folders (unlike files, which have an explicit `id`). This has only ever been exercised by user/system, both `is_protected` (so `delete_folder` is never actually called on them). Before adding the first deletable folder, verify sibling sub-resources embedded in the same `.tres` get distinct `resource_path` values — if not, give `FolderData` an explicit `id` field like `FileData` already has.

### Apps (`scripts/apps/`, `scenes/apps/`)

Each app (`NoteViewer`, `FilesApp`, `DevCrackApp`, `TaskManagerApp`, `TrashApp`, `KikuChatApp`, `SystemLogApp`, `MosMailApp`) is a standalone `Control` scene, instantiated by whoever wants to open it (`Desktop`, or another app) and handed to `WindowManager.open_window`. Only call an app's configuration methods (e.g. `unpack(file)`, `show_plain(text)`, `TaskManagerApp.self_window_id = ...` / `.refresh_list()`) **after** `open_window` has added it to the tree — its `@onready` references aren't valid before that.

`FilesApp` is a full file browser over the `FolderData`/`FileData` tree rooted at `data/drive.tres`. Back/forward navigation, the current path, and the hidden-files toggle are all plain state on the `FilesApp` instance (`_history`, `_history_index`, `_show_hidden`) — never on the resources themselves, per the immutability rule above. Entering a new folder truncates any forward history, like a browser. Folders sort before files, hidden entries (`is_hidden`) are omitted unless the toggle is on, locked files are shown identically to unlocked ones — no `(locked)` suffix, no distinct color, nothing in the row hints at lock state — but `_open_file` refuses to open one directly, surfacing a warning dialog instead — see below — and trashed files/folders (`GameState.is_file_deleted`/`is_folder_deleted`) are omitted entirely. Double-clicking a file that already has an open `NoteViewer` window calls `WindowManager.reveal_window` instead of opening a duplicate (`_open_file_windows`, keyed by `FileData.id`); a second, separate `_devcrack_windows` map does the same for DevCrack windows, since a file can have both a `NoteViewer` and a `DevCrackApp` window open on it at once. `Desktop` does the same single-instance pattern for the apps it launches itself (drive icon, README, SYSTEM.LOG, task manager, trash) via its own `_singleton_windows` map keyed by an arbitrary app key (see `_focus_if_open`).

Right-clicking a file row opens a `ContextMenu` (see below) with "Open" (same effect as double-click — `_open_file`), "Unpack through DevCrack" (`_open_devcrack`, always offered, on every file regardless of extension), and "Delete" (`GameState.delete_file`, then `_close_all_windows_for(file)`) *only if* `GameState.can_delete_file` is true — protected files just don't get a "Delete" item at all, same pattern as desktop icons with no `delete_action` (see `DesktopIconUI`/`Desktop._wire_icon` below). Folder rows get the same "Open"/"Delete" pair (via `GameState.can_delete_folder`) but no unpack option — DevCrack only ever operates on files; deleting a folder recurses `_close_open_windows_under(folder)`, which calls `_close_all_windows_for` per file so nothing dangles either level down. `_close_all_windows_for(file)` is the one place that knows a file can have both an `_open_file_windows` (`NoteViewer`) and a `_devcrack_windows` (`DevCrackApp`) entry open at once and closes whichever exist — deleting a file used to only check the former, leaving a stray DevCrack window behind. Which target the menu acts on is tracked in `_context_target_file`/`_context_target_folder` (exactly one set at a time) rather than rebinding the shared menu's signal per row. `_open_file` now refuses any `GameState.is_locked(file)` file — not just `.mos` ones — via `warning_dialog.show_message(...)` instead of opening a window (see `WarningDialog` below), branching on `GameState.get_lock_reason(file)` for the wording: `CORRUPTED` gets "ไม่สามารถเปิดไฟล์นี้ได้เนื่องจากไฟล์เสียหาย" (this much *is* realistic OS-style error differentiation — corrupted vs. merely access-denied is a distinction a real file system would surface), everything else (`PROTECTED`) gets the plain "ไม่สามารถเปิดไฟล์นี้ได้". Neither message points the player at DevCrack, names an entry, or explains *how* to fix it — that stops-short-of-a-walkthrough line is the deliberate house rule here (see `DevCrackApp` below for the same principle applied to REPACK's feedback, which stays silent even for `CORRUPTED`). `_open_devcrack` opens/reveals a `DevCrackApp` window the same way `_open_file` does for `NoteViewer`, and additionally connects to that `DevCrackApp` instance's `file_repacked` signal — a repack changes `GameState`'s archive-entry-disabled state, which nothing else tells `FilesApp` about (there's no dedicated signal for it the way `trashed_changed` covers deletes), so `_on_file_repacked` calls `_rebuild_list()` (row appearance no longer varies with lock state — see above — so this rebuild currently has no visible effect, but the connection is kept as the one place `FilesApp` would learn of a repack if a row ever needs to react to one again). This connection is made fresh per `DevCrackApp` instance (never reused, unlike the shared dialogs), so no duplicate-connection guard is needed.

`DevCrackApp.unpack(file)` is reachable from any file via "Unpack through DevCrack" — no extension filtering, the engine doesn't interpret filenames specially — and **is never itself gated by lock state**: `FilesApp` calls it unconditionally, with no equivalent of the `is_locked` check `_open_file` does. This is deliberate, not an oversight — DevCrack is the *tool* that acts on a file's lock state, so gating entry into it on that same lock state would be circular (there used to be a `has_learned_devcrack` flag gating unpack on any locked file until the player had first repacked a non-locked one — but every puzzle file is locked now, so that flag could never be set on a fresh game and every file would permanently soft-lock; it's been removed along with the "gate" state/`GateLabel` it drove). It renders one row per `BlobData` "archive entry" on the file (all of them, always — entries are never removed from the list, see below) — each entry has its own `filename`/`extension` (e.g. `a1.data`, falling back to `label` alone if `filename` is empty, for older content like `meta_tag`'s blob that predates those fields) and, on the right of the row, either its `last_modified` flavor string or the word "offline" if the entry is currently disabled. No row styling may hint which entries are `should_remove` before the player has touched them — every row looks identical, aside from that flavor text, until the player's own toggling changes it — which is also why DevCrack carries no in-app hint text at all (`FileData` has no `reveals_clue`-style field; the puzzle is trial-and-error only). Right-clicking a row opens the app's own `ContextMenu` instance with "Copy"/"Paste"/"Disable" (or "Enable", labeled dynamically from current state) — same right-click-not-always-visible-buttons convention as `FilesApp` — tracked via a single `_context_target_blob` (only one target type here, unlike `FilesApp`'s file/folder pair). Copy/Paste are still stubs; selecting either just calls `warning_dialog.show_message("ยังไม่รองรับฟังก์ชันนี้")` (see `WarningDialog` below) instead of doing anything. The toggle action calls `GameState.set_archive_entry_disabled(file, blob.id, ...)`, flips the row to 50% opacity + "offline" (`row.modulate.a`, no new `Palette` color needed), and — critically — **is reversible in both directions**: re-enabling a `should_remove` entry re-`PROTECTED`-locks the file, and *disabling* a non-`should_remove` entry (essential data, not the intended block) locks it too, as `CORRUPTED` — the player broke the archive by removing something that wasn't meant to go. Both conditions clear the moment the relevant entry is toggled back, since `GameState.get_lock_reason(file)` is computed live from current disabled-state on every call, not cached from a one-time "repack succeeded" flag (there's no `repacked_files`/`is_repacked`/`mark_repacked` anymore). Row styling never distinguishes `should_remove` from non-`should_remove` entries — same "no advance hints" rule as before — so `CORRUPTED` is never discoverable from the row list itself or from REPACK's feedback (see below); the only place it surfaces at all is `FilesApp`/`Desktop._open_readme`'s open-attempt message, which says "ไฟล์เสียหาย" ("file corrupted") — realistic OS-style error differentiation, not a puzzle hint, since it still never says *which* entry or *how* to fix it. By convention every file's `should_remove` entry is named `data.protected` (both `def_mos.tres` and `forbidden_file.tres` set it that way — that blob is what makes the file `PROTECTED`-lockable specifically; `CORRUPTED` needs no `should_remove` blob at all, see above) so the player learns to recognize what to look for. `REPACK` (bottom-right, via `BottomBar`'s `alignment = ALIGNMENT_END` with the `Scroll` above it eating all flexible height) is **never gated** either — the player can press it anytime regardless of current entry state, there's no pass/fail validation blocking the click itself. `_on_repack_pressed` does not branch on outcome at all — it calls `GameState.on_devcrack_repacked()` unconditionally first (a flat 70% chance per press of spawning a `"lived.process"` ghost entry, regardless of which file or what the repack's outcome is — see `GameState` above for the full cascade), then emits `file_repacked(current_file, unlocked)` (still computed from `GameState.get_lock_reason(current_file)`, for any future listener that cares), then unconditionally pops `warning_dialog.show_message("repack เสร็จสิ้น")` and closes its own window via `window_manager.close_window(self_window_id)` (both `window_manager` and `self_window_id` are set by `FilesApp._open_devcrack` the same way `TaskManagerApp.self_window_id` is set by `Desktop` — `window_manager` before `open_window`, `self_window_id` from the returned `AppWindow` after). This is deliberate: a real repack tool performs the operation and reports "done," it doesn't sit there judging whether the result happens to be openable — that's what `FilesApp`'s own lock check is for, discovered separately the next time the player tries to open the file. There is no `feedback_label` anymore (removed along with the branching) — every repack looks identical from the player's side regardless of `PROTECTED`/`CORRUPTED`/`UNLOCKED`. Same "no naming a specific entry, no explaining the cause, no suggesting a next step" house rule as `FilesApp._open_file`'s messages — those *do* now distinguish `CORRUPTED` from `PROTECTED` in wording (see above), but REPACK stays silent regardless: puzzle knowledge is game content the player has to work out, not something the tool's own UI leaks.

`TaskManagerApp` (`task_manager_app.gd`) lists every open window as a process row, driven entirely by `WindowManager.get_open_windows()`, alongside two other sources of background-noise rows: a fixed set of `SYSTEM_PROCESSES` and `GameState`'s live ghost-process list (see `GameState` above for the full cascade). Every row built by `_rebuild_list()` is normalized to the same shape — `{kind: "system"/"window"/"ghost", id, title, killable}` — before being handed to `_add_process_row(id, kind, title, killable)`, so the row builder and its right-click menu don't need to know which of the three sources a row came from.

- `SYSTEM_PROCESSES` (`const Array[Dictionary]` of `{name, hidden}` in the script — pure flavor text; not backed by any resource or `GameState`, since it's cosmetic noise, not puzzle content) is 20 always-visible entries (e.g. `mos_kernel`, `compositor.sys`) plus a handful of `hidden = true` ones (e.g. `unlisted_user.sys`, `null_shell.daemon`) that only show up with "show hidden" on — same "no advance hints" rule as everywhere else, they read as ordinary background noise until the player notices they only appear with the toggle on. `kind = "system"` rows are always `id = ""`, `killable = false`.
- `kind = "window"` rows come straight from `window_manager.get_open_windows()` (skipping `self_window_id`, same as before) and are always `killable = true` — real windows have no concept of "hidden," so they're never filtered by the show-hidden toggle.
- `kind = "ghost"` rows come from `GameState.get_ghost_processes()`, filtered by both the entry's own `hidden` flag and the show-hidden toggle (same rule as `SYSTEM_PROCESSES`'s hidden entries) — `id`/`title`/`killable` are taken directly from the `GameState` entry (`entry.id`, `entry.name`, `entry.killable`), so a `"ssecorp.devil"` that rolled `killable = false` renders with its "Kill process" item disabled, identically to a `system` row.

The show-hidden toggle (`_show_hidden`, `HiddenToggleButton` in a new `HeaderBar` row alongside `HeaderLabel` — same layout/text convention as `FilesApp`'s own hidden-files toggle: `"[ ] show hidden"` / `"[x] show hidden"`, `_on_hidden_toggled`/`_update_hidden_toggle_text`) gates the hidden `SYSTEM_PROCESSES` entries and hidden ghost entries identically — this is the only way `ssecorp.devil` (always `hidden = true`) is ever visible at all.

`_rebuild_list()` builds a "background pool" — filtered `system` rows, then filtered `ghost` rows appended after — and interleaves `window` rows evenly among that pool using the same spacing formula as before (`pos = round((i+1) * pool_count / (app_count+1))`, inserted at `pos + i`); only what feeds the pool changed, not the interleaving math. Every row — system, window, or ghost — is built by the same `_add_process_row(id, kind, title, killable)`: a `PanelContainer` wrapping a `MarginContainer` (`margin_right = 4`, on top of `task_item_style()`'s own equal-on-every-side content margin, since without it `"running..."` reads as flush against the row's right edge) wrapping an `HBoxContainer` of a name `Label` (`SIZE_EXPAND_FILL`) plus a `"running..."` status `Label` (`Palette.TEXT_FAINT`) sharing the one box, rather than sitting in separate widgets. The row's box is only visible on hover — its `panel` stylebox override starts as `Palette.task_item_style_invisible()`, and the row's own `mouse_entered`/`mouse_exited` signals (`PanelContainer` has no built-in hover state the way `Button` does) swap it to `Palette.task_item_style()` and back; it's the invisible variant specifically, not a bare `StyleBoxEmpty`, so the row's minimum size (border width + content margin) never changes between the two states and the list doesn't jump. `gui_input` is connected on the `PanelContainer` itself, not on either label, bound with `(id, kind, killable)`. Visually and input-wise all three kinds are identical (aside from the flavor-text `title`) — nothing hints at `kind`, same "no advance hints" rule as `DevCrackApp`'s entry rows.

Double-clicking a row calls `WindowManager.reveal_window(id)` only when `kind == "window"` — `system`/`ghost` rows aren't real windows, so there's nothing to reveal. Right-clicking opens the app's own `ContextMenu` instance with a single "Kill process" item, tracked via `_context_target_id`/`_context_target_kind` (replacing the old single-target `_context_target_window_id` now that a row's target needs both an id and which source it came from), passed `"disabled": not killable` — `ContextMenu.open_at` renders a disabled item at half opacity (`modulate.a = 0.5`, same convention `DevCrackApp` uses for disabled archive-entry rows) and never wires its `pressed` signal, so an unkillable row's menu item is visibly present but inert rather than absent — this is also how a `killable = false` `"ssecorp.devil"` row behaves: clicking "Kill process" on it does nothing at all, identical to a `system` row, and there's no warning message telling the player why. `_on_context_item_selected` branches the actual "kill" action on `_context_target_kind`: `"window"` calls `window_manager.close_window(id)` (unchanged), `"ghost"` calls `GameState.kill_ghost_process(id)` (which owns the `lived.process` → `ssecorp.devil` cascade itself — `TaskManagerApp` does nothing extra), and `"system"` is a no-op guard (never actually reachable since its menu item is always disabled, but kept rather than assumed unreachable).

It re-subscribes to `window_opened`/`window_closed` *and* `GameState.ghost_processes_changed` to rebuild the list live (same "shared signal, subscriber rebuilds" pattern `TrashApp` uses for `trashed_changed`), and takes a `self_window_id` (set by `Desktop._open_task_manager` right after `open_window` returns, followed by an explicit `refresh_list()` call) so it can filter its own row out — it can't rely on the window-opened signal alone, since that fires for it before `self_window_id` is assigned. Its `Scroll` node's `VScrollBar` is thinned and reskinned in `_ready()` (`custom_minimum_size.x = 3`, flat `Palette`-derived `scroll`/`grabber`/`grabber_highlight`/`grabber_pressed` styleboxes) — the engine's default scrollbar width reads as oversized against this app's tiny 384×216-space rows and font, the same category of issue as the `CheckBox` theme-icon gotcha documented under Display settings above, just fixed here instead of avoided.

`TrashApp` (`trash_app.gd`) lists everything `GameState` has trashed (folders first, then files, `readme.txt` last among file-likes), rebuilt on `GameState.trashed_changed`. Each row has a `[restore]` button bound to `GameState.restore_file`/`restore_folder`/`restore_readme` via a `Callable.bind()` per row — restoring a file/folder just erases its trashed-dictionary entry and re-emits `trashed_changed`; `FilesApp` picks the change up automatically on its next `_rebuild_list()` since it already checks `GameState.is_file_deleted()`/`is_folder_deleted()` every time, so no change to `FilesApp` was needed. Restore has no protected/undeletable equivalent — anything that was successfully trashed can always be restored.

`KikuChatApp` (`kikuchat_app.gd`) is a read-only LINE-style chat log, unlocked by a password — **a mechanic entirely independent from the DevCrack/blob lock system described above**. Nothing here extends `FileData`, carries `blobs`, or is ever passed to `GameState.get_lock_reason()`; conflating the two is the single mistake to avoid when touching this app. Its data model lives in `scripts/resources/` alongside (but structurally separate from) `FileData`/`FolderData`/`BlobData`: `ChatMessageData` (`sender`, `text`, `date`, `timestamp` — `date` is Thai-formatted flavor text like `"19 สิงหาคม 2569"`, separate from `timestamp`'s time-only string; every message in a thread's `.tres` carries one, and it's what `_add_date_divider()` groups on, see below; `image: Texture2D`, optional and left null on every message today — the first actual image sprite field anywhere in the game), `ChatThreadData` (`id`, `contact_name`, `last_message_preview`, `requires_code: bool`, `messages`), and the root `KikuChatListData` (`access_code: String`, `threads`) — saved as `data/kikuchat/chat_list.tres` referencing four `data/kikuchat/threads/*.tres` files. `messages`/`threads` are deliberately plain `Array`, not `Array[ChatMessageData]`/`Array[ChatThreadData]` — same as `FileData.blobs` — because a typed array of a custom `class_name` `Resource` whose elements are loaded through a `.tres` → `.tres` reference chain (as `chat_list.tres` → each thread's own file is, unlike `blobs`' same-file sub-resources) trips a Godot type-validation bug where an element resolves to its own attached `Script` instead of an instance at runtime ("argument should be `ChatThreadData` but is `res://.../chat_thread_data.gd`"); untyped sidesteps it entirely. The password is single and app-wide (`KikuChatListData.access_code`), not per-thread; `ChatThreadData.requires_code` just gates whether a given thread needs that one code entered first. `KikuChatApp` is the only thing that ever reads `access_code` or compares it — `GameState.is_app_unlocked_by_code("kikuchat")`/`unlock_app_with_code("kikuchat")` (see `GameState` above) only remember *whether* the code has been entered correctly, keyed by an `app_id` string chosen entirely by the caller specifically so a future app (e.g. MosMail) can reuse the same two methods with its own `app_id` and get a fully independent password/unlock state for free, no `GameState` changes required. Unlike every other app here, the window is a **persistent two-pane split** (LINE-PC-style), not a single view or a list/detail toggle: `Sidebar` (a plain `VBoxContainer`, fixed `custom_minimum_size.x = 55`, no stylebox of its own) stays visible at all times on the left, `ChatPane` fills the remaining width on the right, and switching threads never hides either — there's no `< back` button because there's nothing to navigate back from. This is also why `NoteViewer`/BBCode isn't used for messages at all here (unlike every other text-content app, e.g. `readme.txt`'s `content`): `RichTextLabel` BBCode can format text but can't draw a bordered per-message box, and the mockup this app matches needs individually-colored, individually-bordered chat bubbles, so each message is its own real node tree instead (`_add_message_bubble`, see below). The divider between the two panes is its own dedicated `Divider` `ColorRect` (`Palette.BORDER`, 1px wide) sitting between `Sidebar` and `ChatPane` as a *sibling* in `HBox`, not a border baked into `Sidebar`'s own stylebox — a selected/hovered row's opaque background is a descendant of `Sidebar` and would otherwise render on top of (and hide) a border that lived on `Sidebar` itself, since Godot draws a node's entire subtree before moving on to its next sibling; a later sibling in `HBox` is guaranteed to draw after — on top of — everything inside `Sidebar`, so the line stays visible even across the active row. `ChatPane` is a `MarginContainer` (`margin_left = 5`, matching the same inset the app's own root `HBox` already uses; `margin_right = 2`, deliberately smaller — see below — wrapping an inner `ChatBody` VBox) purely so bubbles and the header don't sit flush against the window edge — `Sidebar` needs no matching margin since its own rows already carry padding via `chat_contact_row_style`'s content margin. `MessagesScroll`'s `VScrollBar` floats over its content's right edge rather than reserving space for itself (a `ScrollContainer` quirk, not something `_style_scrollbar` controls) — since message rows stretch full-width and a "me" bubble is pushed flush against that same right edge, the scrollbar would otherwise sit directly on top of its timestamp whenever the thread is long enough to scroll. `MessagesMargin`, a `MarginContainer` wrapping `MessagesList` inside `MessagesScroll` (`margin_right = 4`, roughly the scrollbar's own width plus a hair of buffer, **and `size_flags_horizontal = 3`** — without that flag a `MarginContainer` shrinks to its own content's minimum width instead of filling the `ScrollContainer`'s viewport, which silently breaks every bubble's left/right alignment since `_add_message_bubble`'s spacer trick then has no extra width to push into and everything collapses toward the left regardless of sender), reserves that space unconditionally instead, so the layout doesn't shift depending on whether a given thread is long enough to actually need scrolling. `ChatBody`'s last child is `InputField`, a `LineEdit` permanently `editable = false` (never toggled — this app is read-only end to end, not just its threads) styled via the `read_only`/`font_uneditable_color` theme slots `LineEdit` exposes specifically for that state, always showing the literal text "ไม่สามารถตอบกลับได้ เนื่องจากไม่ได้ยืนยันตัวตน" — not a placeholder, the box's actual (unchangeable) content — so the player can see where a reply would go and that it doesn't work, rather than there being no input at all.

`Sidebar` renders one `_add_contact_row(thread)` per `CHAT_LIST.threads` entry — a small avatar square (`Palette.icon_glyph_style()`, same builder `DesktopIconUI`'s glyph box uses, `custom_minimum_size = Vector2(9, 9)`, showing `contact_name.substr(0, 1)`) sitting close to the row's left edge (`hbox` separation `2`, row content margin `2`) plus a stacked name/`last_message_preview` pair — with **no visual hint of `requires_code`**, same "no advance hints" rule `FilesApp` follows for locked files. `avatar` additionally sets `size_flags_horizontal`/`size_flags_vertical = SIZE_SHRINK_CENTER` and `avatar_label.clip_text = true` — a plain `Panel` with only `custom_minimum_size` set still lets Godot grow its actual rect past that minimum when the row has slack (e.g. a taller row from a longer `last_message_preview` wrapping), which read as "the avatar box isn't a consistent size"; `SHRINK_CENTER` pins it to exactly `custom_minimum_size` regardless. Every child inside a row (`avatar`, `avatar_label`, `text_box`) is explicitly `mouse_filter = MOUSE_FILTER_IGNORE` so a click anywhere in the row — including directly over the avatar square — always reaches the row's own `PanelContainer.gui_input`, never gets swallowed by a child first, and a single left click (not a double-click, unlike `FilesApp`'s file rows) is enough to select a thread. A row's box comes from `Palette.chat_contact_row_style(selected, hovered)`: unlike `TaskManagerApp`'s hover-only box, this one is a flat list row (bottom divider only) that's always visible, just recolored per state — `WINDOW_BG` at rest, `TITLEBAR_BG` on hover (via `mouse_entered`/`mouse_exited`, guarded so hovering the *selected* row never overwrites its selected color), `TITLEBAR_BG_ACTIVE` when selected. There's deliberately no left accent bar on top of that background swap (an earlier version had one) — the recolored background alone is already enough signal for which row is active, so a second redundant indicator was cut. Selecting a different thread just calls `_rebuild_sidebar()` (cheap at 4 rows) rather than patching styles on the two affected rows individually, the same "just rebuild the list" idiom used everywhere else in this codebase. Both `ContactsScroll` and `MessagesScroll` get the same thinned/reskinned `VScrollBar` treatment `TaskManagerApp` applies to its own `Scroll` node (`_style_scrollbar`, factored into a shared helper here since this app needs it twice).

A single left click on a row (`_on_contact_row_gui_input`, checking only `event.pressed and event.button_index == MOUSE_BUTTON_LEFT` — no `event.double_click`, unlike `FilesApp`) calls `_select_thread(thread)`: if `requires_code` is false, or true but already unlocked, it sets `_selected_thread` and re-renders both panes immediately; otherwise it stashes the thread in `_pending_thread` and opens `KikuChatApp`'s own `PasswordDialog` instance (see below) via `ask(...)`, connecting `submitted`/`cancelled` with `CONNECT_ONE_SHOT` guarded by `is_connected()` each time (`_connect_password_dialog_once`, same double-connect guard `Desktop._confirm_shutdown` uses for its shared `ConfirmDialog`, since one `PasswordDialog` instance is reused for every locked thread this app ever opens). `_on_password_submitted` compares the entered text (`strip_edges()`ed, same trim `login_screen.gd` applies) against `CHAT_LIST.access_code` — a match calls `GameState.unlock_app_with_code`, then selects `_pending_thread` the same way a successful `_select_thread` call would; a mismatch just pops `warning_dialog.show_message("รหัสผ่านไม่ถูกต้อง")` with no retry loop. `_on_password_cancelled` only clears `_pending_thread`, leaving whatever was already shown untouched.

`_render_chat_pane()` sets `ChatHeader` to the selected thread's `contact_name` (empty, with a `Palette.TEXT_FAINT` placeholder line in `MessagesList`, before anything's ever been selected — there's no default-open thread on boot) and rebuilds `MessagesList`, walking the thread's messages with a local `previous_date` and `is_first_message` (plain loop variables, not class fields — there's nothing else that needs them) and calling `_add_date_divider(message.date)` before `_add_message_bubble(message)` whenever `is_first_message` or `message.date` differs from `previous_date`. `is_first_message` is its own flag rather than relying on `previous_date`'s initial `""` sentinel to differ from a real message's `date` — if a message's `date` were ever genuinely empty, the sentinel comparison would silently skip the divider on the thread's first message; every message in every thread's `.tres` always sets a non-empty `date` today, but the explicit flag doesn't depend on that holding. `_add_date_divider(date_text)` is a full-width row — a `ColorRect` line (`Palette.BORDER`, 1px tall, `SIZE_EXPAND_FILL`) either side of a centered `Label` (`Palette.font_body`, `Palette.TEXT_DIM`, smaller than a bubble's own text) with the `HBoxContainer`'s `separation` keeping the label off the lines — added straight into `MessagesList` as its own row, deliberately outside `_add_message_bubble`'s spacer-based left/right alignment trick (see below), since a divider has no sender to align to. One `_add_message_bubble(message)` per message: a `PanelContainer` (`Palette.chat_bubble_style(is_me)` — `TITLEBAR_BG` for `sender == "me"`, `DESKTOP_BG_2` for the contact, same bordered-box shape as `task_item_style()` just different fill) wrapping an inner `bubble_content` `VBoxContainer` — `PanelContainer` only lays out a single child, so an optional image and/or text both go inside that one inner box rather than being added to the bubble directly. A `message.image` (see `ChatMessageData` above) becomes a `TextureRect` fixed at `BUBBLE_WIDTH`: `custom_minimum_size` is computed by hand as `Vector2(BUBBLE_WIDTH, BUBBLE_WIDTH * texture_size.y / texture_size.x)`, and `expand_mode` is explicitly set to `EXPAND_IGNORE_SIZE` — without that, `TextureRect`'s default `expand_mode` (`EXPAND_KEEP_SIZE`) reports the *texture's own native pixel size* as its minimum size regardless of `custom_minimum_size`, so a full-resolution photo would render at its actual (much larger) size instead of shrinking to fit the bubble. `stretch_mode = STRETCH_SCALE` then fills that now-correctly-sized box. No manual filter override needed, since `project.godot`'s `textures/canvas_textures/default_texture_filter = Nearest` already applies and this is the first sprite in the game to actually exercise that setting. `message.text` becomes a `Label` fixed at the same `BUBBLE_WIDTH` with `autowrap_mode = AUTOWRAP_WORD` (every bubble wraps at the same fixed width rather than shrinking to its own content with a max cap — Godot's container sizing doesn't give a reliable "shrink but cap" for autowrapped `Label`s at this scale) — skipped entirely when `text == ""` (an image-only message) rather than added-but-empty, same convention `SystemLogApp`/`MosMailApp` use for a blank field. Every bubble still gets a `Palette.TEXT_FAINT` timestamp line below it regardless, right-aligned for "me" and left-aligned for the contact. Each bubble sits in an `HBoxContainer` with a `SIZE_EXPAND_FILL` spacer on the side opposite its sender — spacer-before for "me" (pushes the bubble right), spacer-after for the contact (keeps it left) — which is what actually produces the left/right alignment, not the text alignment inside the bubble itself. After rebuilding the list, `_render_chat_pane()` calls `_scroll_to_latest_message()` so opening/switching a thread always lands on its most recent message rather than leaving `MessagesScroll` at the top. A single `await get_tree().process_frame` isn't reliable here: on a pane's very first render, `MessagesScroll`'s scrollable range keeps changing for more than one frame as minimum-size propagates up through `MessagesMargin` → `MessagesList` → each bubble's autowrapped `Label` (later re-renders are mostly already warm, so this matters most the first time), so scrolling after only one frame can land short of the bottom. Instead it reapplies `scroll_vertical = get_v_scroll_bar().max_value` every frame in a loop, breaking out once `max_value` stops changing between frames (capped at 5 frames so a layout that never settles can't loop forever).

`SystemLogApp` (`system_log_app.gd`) is the desktop's "SYSTEM.LOG" window — old boot/account/anomaly history for the machine, replacing what used to be a single hardcoded `Label` built inline in `Desktop._open_system_log()`. Structurally it's the plainest app here, closer to `TrashApp` than `KikuChatApp`/`DevCrackApp`: no navigation state, no selection, just `header_label` + `ScrollContainer` + `List`, rebuilt once from static data with nothing to subscribe to (a comment in `_ready()` notes that a future GameState-driven log would need the equivalent of `TrashApp`'s `GameState.trashed_changed.connect(_rebuild_list)`). Its data model is `LogEntryData` (`datetime` — a single `"YYYY-MM-DD HH:MM:SS"` string, not split like `ChatMessageData`'s `date`/`timestamp`, since nothing here needs to compare dates to draw dividers; `level` — a plain `"INFO"`/`"WARN"` string, no enum; `message`; `actor` defaulting to `""` — every current entry in `log.tres` sets one, but the field stays optional for any future entry that's genuinely nobody's doing) and the root `SystemLogListData` (`entries: Array`), both saved as a single `data/system_log/log.tres`. `entries` was originally typed `Array[LogEntryData]` on the theory that same-file sub-resource embedding (like `FolderData.subfolders`/`.files` in `drive.tres`) would sidestep the `KikuChatListData.threads`/`ChatThreadData.messages` bug (see `KikuChatApp` above) — it didn't: at runtime every element resolved to its own attached `Script` instead of an instance (`"argument 1 should be LogEntryData but is res://scripts/resources/log_entry_data.gd"`), the exact same failure mode, just triggered by something else — most likely that `log_entry_data.gd`/`system_log_list_data.gd` are hand-authored files that had never been opened by the editor (so had no `uid://` yet) at the time `log.tres` was written, unlike `folder_data.gd`/`file_data.gd`'s scripts, whose `.tres` references already carry a `uid=`. `entries` is untyped `Array` now, same workaround as `KikuChat`'s two fields. Entries are hand-ordered oldest-to-newest in the `.tres` (no runtime sort) and span real story time: a couple of very-old entries reference a previous account (`actor = "nattapong.w"`, `actor = "K."`) before the log settles into the current boot's routine `INFO`/`WARN` lines. Every entry carries an `actor` now, not just the human-caused ones — routine system/kernel entries (`"boot sequence completed"`, `"process m-os_core: running"`, `"idle... idle... idle..."`, both `WARN` anomalies) are attributed to `actor = "m-os_core"` (the system itself as the actor, not a person), and `"new user session started"` is deliberately attributed to the dormant `"nattapong.w"` account rather than a fresh one or a blank — implying the current boot never actually created its own account, which is what makes the later `WARN` `"session initiated from unknown device"` (`actor = "???"`, unattributed, deliberately unresolved, mirroring `KikuChatApp`'s unknown-number thread) read as a genuine second, different presence rather than just more of the same ambiguity. Same "no advance hints" rule as everywhere else: nothing here names a blob, `data.protected`, or how any puzzle is solved. `_add_log_row(entry)` builds one `HFlowContainer` per line (not `HBoxContainer`, and with **no** box or hover state at all, unlike every other list row in the game which is at minimum a `task_item_style()`-boxed or hover-boxed `PanelContainer`) — a log is meant to read as continuous flowing text, not a clickable list. `HFlowContainer` specifically because a row's four pieces need to wrap onto a new line instead of clipping/overlapping whenever the window is at its default (small) size or narrower than the row's full content — the same responsive behavior the reference mockup gets from CSS `flex-wrap` — which plain `HBoxContainer` doesn't do on its own. `FlowContainer` doesn't stretch a child to fill a line's leftover width the way `BoxContainer`'s `EXPAND` flag does, so `message_label` gets a fixed `MESSAGE_MIN_WIDTH` floor instead of `SIZE_EXPAND_FILL` (same "give an autowrapped `Label` a stable width instead of relying on expand" idea as `KikuChatApp`'s `BUBBLE_WIDTH`) — sized, along with `DATETIME_WIDTH`, so the longest entries in `log.tres` still fit on one line at the window's default size, matching the reference mockup (which shows every row unwrapped); `HFlowContainer` still wraps a row if the window's ever narrower than that. Each row is `datetime` (`Palette.TEXT_FAINT`, fixed `DATETIME_WIDTH` so entries line up like a table) + a level tag (a border-only `PanelContainer`, no fill — `_log_level_style(level)` returns `Palette.BORDER` border for `"INFO"` vs `Palette.ACCENT_WARN` for `"WARN"`, kept as its own helper specifically so that branch doesn't sit inline in `_add_log_row`; built by hand rather than through `make_flat_style()`'s uniform-margin signature, since matching the mockup's tight `padding: 0 3px` tag needs horizontal-only content margin — same one-off-asymmetric-`StyleBoxFlat`-but-colors-still-from-`Palette` precedent as `Desktop`'s start-menu shutdown row) + `message` (`Palette.TEXT_DIM` normally, bumped to `Palette.TEXT_MAIN` for `WARN` so anomalies read slightly brighter) +, only when `entry.actor != ""`, a trailing `"· by %s"` label (`Palette.TEXT_FAINT`, fixed `ACTOR_WIDTH`) — the node is skipped entirely for a blank actor rather than added-but-hidden. `ACTOR_WIDTH` matters more than it looks: a `clip_text` `Label` with no `custom_minimum_size` reports a near-zero minimum size, which tricked `HFlowContainer` into squeezing the actor label into whatever sliver of space was left on an already-crowded line instead of wrapping it to a fresh one — clipping almost the entire name away right at the row's edge rather than actually wrapping. Giving it the same fixed-floor treatment `datetime_label` already had fixes that. `Desktop._open_system_log()` opens it at a much roomier `Rect2` than the single 3-line `Label` it replaced ever needed — that old tiny window is what made the real multi-column log look broken at first, and it's been widened twice since: once because most rows were still wrapping onto a second line instead of matching the mockup's one-line-per-entry look, and again once `ACTOR_WIDTH` started actually being enforced. Like `KikuChatApp._scroll_to_latest_message()`, `_rebuild_list()` finishes by calling `_scroll_to_latest_entry()` so the window opens already scrolled to the newest entry: a single `await get_tree().process_frame` isn't reliable since the `ScrollContainer`'s scrollable range can take more than one frame to settle after adding all the rows, so it reapplies `scroll_vertical = get_v_scroll_bar().max_value` every frame until that value stops changing (capped at 5 frames).

`MosMailApp` (`mosmail_app.gd`) is a read-only Gmail-style inbox — inbox/spam/trash tabs, a per-email password unlock — reusing `GameState.is_app_unlocked_by_code`/`unlock_app_with_code` with `app_id = "mosmail"` and requiring **zero** `GameState` changes to support, exactly as those two methods were designed to allow (see `GameState` above). `EmailData` (`id`, `sender`, `subject`, `snippet`, `content`, `datetime` — flavor text typed straight into the data like `ChatMessageData.timestamp`, never computed; `is_spam: bool` — fixed per-email flavor, not a toggle, there is no "mark as spam" action anywhere in this app; `requires_code: bool`) never extends `FileData` and is never touched by anything blob-related, the same "completely separate mechanic" warning `ChatThreadData` carries — conflating this with `GameState.get_lock_reason()` is the one mistake to avoid here. The root `MosMailListData` (`access_code`, `emails`) is saved as a single `data/mosmail/inbox.tres` with every `EmailData` as a sub-resource embedded directly in that file, same as `LogEntryData`/`SystemLogListData`. `emails` is a plain `Array`, not `Array[EmailData]`, pre-emptively — not because same-file embedding was tested and failed here too, but because `SystemLogListData.entries` already proved that same-file embedding doesn't reliably dodge the `KikuChatListData.threads` cross-file bug when the `.gd` files involved are freshly hand-authored with no `uid://` yet (see `SystemLogApp` above); `email_data.gd`/`mosmail_list_data.gd` are in the exact same situation, so this skips straight to the proven-safe untyped workaround instead of re-discovering the same failure.

Structurally `MosMailApp` is a list/detail toggle (two mutually-exclusive states swapped via `_show_state("list"/"detail")`, same idiom as `DevCrackApp._show_state`) — **not** a persistent split-pane like `KikuChatApp`. `_show_state()` toggles `DetailMargin` (a `MarginContainer`, `margin_left`/`margin_right = 5`), not `DetailBox` itself — list rows already get their own left inset from `_email_row_style()`'s content margin, but `DetailBox`'s children (back button, header labels, the embedded `NoteViewer`) had nothing of their own, so without this wrapper the email's content sat flush against `MainArea`'s edge. That difference is also why opening an email is double-click (`_on_email_row_gui_input`, checking `event.double_click` the same way `FilesApp._on_file_row_gui_input` does) rather than `KikuChatApp`'s single click: a temporary list/detail swap doesn't need single-click's extra responsiveness the way a persistent always-visible chat pane does. A locked email (`requires_code` and not yet unlocked via `APP_ID`) stashes itself in `_pending_email` and opens `MosMailApp`'s own `PasswordDialog` instance (`_connect_password_dialog_once`, copied directly from `KikuChatApp`'s identical guard rather than inventing a new flow) — right on match it calls `GameState.unlock_app_with_code(APP_ID)` and opens the pending email's detail view immediately; wrong pops `warning_dialog.show_message("รหัสผ่านไม่ถูกต้อง")`. Right-clicking a row opens `MosMailApp`'s own `ContextMenu` with a single "Delete" item (`GameState.delete_email(email)`, then `_rebuild_email_list()`) — **except** in the trash tab, where the right-click branch is skipped entirely (`_current_tab != "trash"` guards it) rather than opening an empty menu, since restoring happens through a `[restore]` button grown onto each row instead (same `TrashApp._add_row` pattern, bound to `GameState.restore_email(email)`). The email list itself (`_rebuild_email_list`) filters `MAIL_LIST.emails` by `_current_tab`: `inbox` is `not is_spam and not is_email_deleted`, `spam` is `is_spam and not is_email_deleted`, `trash` is `is_email_deleted` alone (ignoring `is_spam` — a spam email that's trashed only shows in trash, not spam). No visual hint of `requires_code` anywhere in a row — same "no advance hints" rule as `FilesApp`'s locked files and `KikuChatApp`'s locked threads. Deliberately not implemented: the reference mockup's green unread-dot and matching bright/dim sender text — that's an unread indicator, and `EmailData` carries no such field (the original spec explicitly excluded read/unread tracking), so every row renders identically regardless of what the mockup shows there. A row itself is a flat bottom-divider row via a local `_email_row_style(hovered)` helper (`Palette.WINDOW_BG`/`TITLEBAR_BG` fill, `Palette.BORDER` bottom line only, `"8px 12px"`-equivalent content margin) — not a `task_item_style()`-boxed row like `DevCrackApp`/`TaskManagerApp` use — matching the mockup's contiguous list-with-hover look; `List`'s own separation is `0` so each row's bottom border is the only divider between rows, the same contiguous convention `KikuChatApp.ContactsList` uses. Built locally rather than reusing `Palette.chat_contact_row_style()` (structurally the same shape) since that builder's content margin is tuned for KikuChat's much narrower sidebar rows, not this roomier one, and an email row never needs `chat_contact_row_style()`'s persistent `selected` state — clicking one immediately leaves the list entirely. Clicking a sidebar tab (`_on_tab_row_gui_input`) always drops back to list state for the newly-selected tab even mid-read in detail state — there's no "remember where I was per tab" behavior, `_current_tab` is plain instance state (not `GameState`, since it's UI state rather than progress, same as `FilesApp`'s `_show_hidden`).

Two Palette-driven widgets worth calling out: the sidebar tabs use the new `Palette.sidebar_tab_style(selected, hovered)` rather than reusing `start_menu_item_style()` — both are left-accent-bar flat rows, but `start_menu_item_style()` only has a `hovered` bool (start menu items never stay selected) while a sidebar tab needs `chat_contact_row_style()`-style persistent `selected` state independent of hover, and its content margins are tuned for a ~46px sidebar column rather than the start menu's much wider rows — parameterizing one builder to cover both would've forced every existing `start_menu_item_style()` call site to also pass a meaningless `selected` argument. And the detail pane embeds one `NoteViewer` instance as a *child* of `MosMailApp` (inside `NoteViewerSlot`, anchored full-rect by hand) rather than as a window's entire content the way every other `NoteViewer` usage in the game works — `WindowManager.open_window()` only auto-anchors the top-level content it's given (`MosMailApp` itself here), so nesting `NoteViewer` one level deeper needs that same `set_anchors_preset(PRESET_FULL_RECT)` call made explicitly once in `_ready()`. `show_plain(email.content)` is called fresh every time an email is opened, exactly like `FilesApp._open_file` does for any other file's `NoteViewer` window. `DetailSubjectLabel` renders through `Palette.font_body` (VT323), not `font_chrome` (Press Start 2P) — `font_chrome` is a Latin-only pixel font with no Thai glyph coverage, so every subject in `inbox.tres` (all Thai) rendered through it with vowel/tone marks mis-stacked onto whatever fallback font Godot substituted in, instead of positioning correctly. `font_body` is what every other Thai string in the game already goes through; `font_chrome` should stay reserved for chrome/UI labels that are always English (window titlebars, `header_label`s, etc.), never for content that might be Thai.

A `TopBarDivider` `ColorRect` (`Palette.BORDER`, 1px, same convention as `Body`'s own `BodyDivider` between `Sidebar` and `MainArea`) separates the top bar from everything below it. The top bar's search field is decorative only — `editable = false` plus `font_uneditable_color`, the exact same inert-but-visible convention `KikuChatApp.InputField` uses, not a new pattern — no filtering is implemented. The "+compose" button is permanently `disabled = true` with `modulate.a = 0.5` and no signal connected at all, same half-opacity/no-handler convention `ContextMenu`'s disabled items and `TaskManagerApp`'s unkillable rows use. The avatar box reads `PlayerIdentity.player_name.substr(0, 1)` (falling back to `"?"` for an empty name) into a `Palette.icon_glyph_style()` box, the same box/builder `DesktopIconUI` and the start menu's row glyphs already use.

### UI components (`scripts/ui/`, `scenes/ui/`)

`ConfirmDialog` (`confirm_dialog.gd`) is a reusable modal: scrim (`Palette.SCRIM`) + `window_style` `PanelContainer` with a message label and `[ ยืนยัน ]` (`blob_marked_style`) / `[ ยกเลิก ]` (`task_item_style`) buttons. Call `ask(message: String)` to show it; it emits `confirmed` or `cancelled` (clicking the scrim outside the panel also cancels). One instance lives on `Desktop` (`_confirm_dialog`, added after the start-menu layer so it renders on top of everything) and is reused across callers — since it's shared, always connect to `confirmed` with `CONNECT_ONE_SHOT` and guard against double-connecting if the same flow can be triggered again before the dialog resolves (see `Desktop._confirm_shutdown`).

`WarningDialog` (`warning_dialog.gd`) is `ConfirmDialog`'s single-button sibling, for messages the player just needs to acknowledge rather than decide on — same scrim + `window_style` `PanelContainer` structure, but only a `[ OK ]` button and only one signal, `acknowledged` (no `cancelled` — there's no second path out). Unlike `ConfirmDialog`, **clicking the scrim does not close it**: the scrim's `mouse_filter = STOP` (set in the `.tscn`) still blocks clicks from passing through to whatever's behind it, but nothing is connected to its `gui_input`, so the only way out is the OK button. Call `show_message(message: String)`. It's instantiated once on `Desktop` (`_warning_dialog`, same pattern as `_confirm_dialog`) but apps that need it don't reach through `Desktop` to find it — it's handed down as a plain `warning_dialog` property, set by whoever opens the app *before* calling `open_window` (same convention as `window_manager`): `Desktop._open_files_app` sets `FilesApp.warning_dialog`, and `FilesApp._open_devcrack` forwards its own `warning_dialog` to the `DevCrackApp` it opens, since `DevCrackApp` is never instantiated directly by `Desktop`. Both apps guard every call with `if warning_dialog:` before using it, the same null-check convention already used for `window_manager`. This replaced an earlier per-app `_show_notice()` (a transient auto-hiding label with a timer) in both `FilesApp` and `DevCrackApp` — that method and its `_notice_label` var are gone from both.

`ContextMenu` (`context_menu.gd`) is a reusable right-click menu: an invisible full-rect `Catcher` (click-outside-to-close, no dimming — unlike `ConfirmDialog` this isn't a modal) plus a `window_style` `PanelContainer` of buttons. Call `open_at(global_pos: Vector2, items: Array)` with `items` as `[{"label": ..., "action": ..., "disabled": ...}]` — `"disabled"` is optional (defaults `false`); a disabled item renders at half opacity (`modulate.a = 0.5`, same convention `DevCrackApp` uses for its own disabled archive-entry rows) and never wires its `pressed` signal, so it stays visible-but-inert rather than being left out of the menu (see `TaskManagerApp`'s "Kill process" item on fake system-process rows). It emits `item_selected(action: String)` (never for a disabled item, since nothing connects its `pressed`) and clamps the panel's position so it never renders outside its own rect. Each button gets `custom_minimum_size.x = MIN_ITEM_WIDTH` so the menu reads as a consistent width regardless of how many items or how short their labels are ("Open" alone shouldn't look narrower than "Open"/"Delete" together) — height is left to shrink-to-content via `panel.reset_size()`, so a single-item menu is exactly one row tall. Each surface that needs one owns a single instance covering that surface's own rect — `FilesApp` (file/folder rows), `Desktop` (desktop icons), `DevCrackApp` (archive-entry rows), and `TaskManagerApp` (process rows) each have their own — and, since that one instance is reused for every row/icon on the surface, the caller tracks "what am I acting on" itself (e.g. `FilesApp._context_target_file`/`_context_target_folder`, `Desktop._context_target_open_action`/`_context_target_delete_action`, `DevCrackApp._context_target_blob`, `TaskManagerApp._context_target_id`/`_context_target_kind`) rather than rebinding `item_selected` per open.

`PasswordDialog` (`password_dialog.gd`) is `ConfirmDialog`'s sibling for KikuChat's code-entry prompt: identical scrim + `window_style` `PanelContainer` structure and the same `[ ยืนยัน ]`/`[ ยกเลิก ]` button styling, plus a `LineEdit` (`CodeInput`, deliberately left with the engine's default `secret = false` rather than a masked password field — the code is meant to be visibly typed) whose `text_submitted` (Enter key) routes through the same path as pressing the confirm button, the same convention `login_screen.gd`'s `name_input` uses. Call `ask(message: String)`; it clears `CodeInput.text` every time so a previous attempt never lingers into the next prompt. It emits `submitted(text: String)` on confirm/Enter or `cancelled` on cancel/clicking the scrim outside the panel (scrim-closes-it here, unlike `WarningDialog` — a wrong code isn't an error that needs acknowledging, it's a decision the player can back out of, same as `ConfirmDialog`). Like `ConfirmDialog`, it has **no idea what a correct code is** — it just reports back whatever text was typed and lets the caller compare it (see `KikuChatApp` above, which checks it against `KikuChatListData.access_code`). Unlike `_confirm_dialog`/`_warning_dialog`, there's no shared instance on `Desktop` — only `KikuChatApp` uses one so far, so it instantiates and `add_child()`s its own in `_ready()`, the same self-contained-instance convention `ContextMenu` already follows in `DevCrackApp`/`FilesApp`/`TaskManagerApp`.

### Desktop shell (`scripts/desktop/`, `scenes/desktop/Desktop.tscn`)

`Desktop` (`desktop.gd`) wires everything together: owns the `WindowManager`, builds taskbar entries from `WindowManager`'s `window_opened`/`window_closed` signals, and builds a start menu (scrim + `PanelContainer`, opened by left-clicking the `start_button`/"M-OS" taskbar button; entries are data in `_start_menu_items`, so adding one is just appending a `{"label": ..., "action": Callable, "glyph": ..., "group": ...}` before `_build_start_menu()` runs). Current entries: my drive, trash, system log, task manager (`group = 0`, navigation), restart, logout, shutdown (`group = 1`, power). `restart`/`logout` both just call `GameState.reset_progress()` then `get_tree().reload_current_scene()` — the duplication is intentional (they read differently to the player but there's currently no state that needs to diverge between them); don't merge them into one function. `shutdown` goes through `ConfirmDialog` (`_confirm_shutdown` → `_do_shutdown`, which shows a black `Palette.VOID` overlay with a "process terminated" message before `get_tree().quit()`).

The start menu has its own look, not a reskinned `task_item_style()` list: `_build_start_menu()` first calls `_build_start_menu_header(vbox)` — a `MarginContainer` with two stacked `Label`s, `"signed in as"` (`Palette.TEXT_FAINT`, `font_size = 4`, the smallest used anywhere in the project) above `PlayerIdentity.player_name` (`Palette.TEXT_DIM`, `font_size = 6` — a size up from the item rows' `5`, since it's the menu's header — `PlayerIdentity` is a plain autoload set once at login by `login_screen.gd` and never touched again here), then a `Palette.BORDER` divider line separating the header from the item list. The loop over `_start_menu_items` calls `_add_start_menu_divider(vbox)` — the same 1px `ColorRect` the header uses — whenever an item's `group` differs from the previous item's (guarded so nothing is inserted before the very first item); this is driven entirely by the `group` field comparison, never a hardcoded index, so adding or removing an entry never needs the divider position updated by hand. Each row (`_add_start_menu_item`) is a `PanelContainer` — not a `Button` like the old single-line list — wrapping an `HBoxContainer` of a glyph box (a small `Palette.icon_glyph_style()` `Panel`, the same box `DesktopIconUI` uses just sized down for a menu row: `custom_minimum_size = Vector2(10, 10)` vs. the desktop icon's `13x13`) and a label. The row's own `panel` stylebox is `Palette.start_menu_item_style(hovered)` — a flat left-accent-bar look (background fill + a border reserved only on the left edge) swapped between hovered/unhovered on `mouse_entered`/`mouse_exited`, the same "swap stylebox, never resize" pattern `TaskManagerApp`'s rows use with `task_item_style_invisible()`/`task_item_style()`; `border_width_left` stays a constant `3` in both states (`TRANSPARENT` at rest, `BORDER_LIGHT` hovered) for the same layout-stability reason. `gui_input` on the row (not a `Button.pressed` signal) checks for a left click and calls `_on_start_menu_item_pressed(action)` — same `_close_start_menu()` then `action.call()` as before, so clicking behavior is unchanged even though the widget underneath it isn't a `Button` anymore. The `"shutdown"` row is the one exception to normal coloring: both its glyph box's border and its label use `Palette.ACCENT_WARN` instead of `Palette.icon_glyph_style()`'s default `BORDER_LIGHT`/`Palette.TEXT_MAIN`, signaling it's the destructive action — the glyph box's stylebox for that row is built inline via `Palette.make_flat_style(Palette.WINDOW_BG, Palette.ACCENT_WARN, 1)` rather than a new named `Palette` builder, since it's a one-off variant of an existing one, not a new reusable look. The menu's width is never hardcoded — `_open_start_menu()`'s existing `reset_size()`/`global_position` positioning (unchanged) naturally sizes the panel to whichever row is widest (`"task manager"`), same as it always auto-sized to the widest button label before this rework.

Ghost-process corruption tints the *whole screen*, not just the desktop background, as ghost processes accumulate: `_ready()` subscribes `GameState.ghost_processes_changed` to `_update_corruption_tint()`, which reads `GameState.get_ghost_process_count()` once and sets two things from it — `background.color = Palette.desktop_corruption_color(ghost_count)` (the desktop's own `ColorRect`, bleeding `Palette.DESKTOP_BG_1` → `Palette.DESKTOP_BG_DANGER`) and `corruption_modulate.color = Palette.corruption_modulate(ghost_count)`. `corruption_modulate` is `CorruptionModulate`, a `CanvasModulate` node living directly on `Desktop.tscn` (sibling of `Background`) — a `CanvasModulate` multiplies its color against every already-rendered pixel in its canvas, so this is what makes windows, the taskbar, icons, and text all bleed red together, not just whatever `Background` covers; `Desktop` is added directly under `Main` (no `CanvasLayer` involved — see `main.gd`), so one `CanvasModulate` here covers everything the player sees. It starts at `Color(1, 1, 1, 1)` (identity — no tint) in the `.tscn`, same "baked default the script immediately overrides in `_ready()`" pattern `Background`'s own scene-file color already follows. `_update_corruption_tint()` is called once up front in `_ready()` too (in case the count is ever nonzero at boot, e.g. after a scene reload that didn't reset progress). `Desktop` never computes either tint itself — it only calls `Palette.desktop_corruption_color()`/`Palette.corruption_modulate()`, per the "never build a color/lerp outside `Palette`" rule.

`DesktopIconUI` (`desktop_icon.gd`) is a generic icon: double-click emits `activated`, right-click emits `context_requested` (both gated to their respective mouse button — `MOUSE_BUTTON_LEFT`/`MOUSE_BUTTON_RIGHT` — so a right-click double-click doesn't also fire `activated`). **Configure it via `configure(glyph, label_text)`, never by assigning the `.glyph`/`.label_text` export vars directly** — Godot runs a child's `_ready()` before its parent's, so by the time `Desktop._ready()` would assign those properties, the icon has already copied its (empty-string default) export values into its labels; the assignment is silently too late. `Desktop._wire_icon(icon, glyph, label, open_action, delete_action = Callable(), unpack_action = Callable())` is the one place that connects both signals: `activated` goes straight to `open_action`, and `context_requested` opens `Desktop`'s shared `ContextMenu` with "Open" plus "Unpack through DevCrack"/"Delete" only if the matching action was passed and is valid — drive/trash/KikuChat are apps with no `FileData`/`FolderData` behind them so they're called with neither and get "Open" only. Icons live in one of two plain `VBoxContainer`s directly on `Desktop.tscn`: `IconGrid` (top-left — drive, trash, KikuChat) and `TopRightIconGrid` (top-right — readme.txt only, currently); there's nothing dynamic about the split, it's just two fixed-offset containers a new icon gets placed into by hand depending on where it should sit.

readme.txt is the one icon that represents an actual file rather than an app, and unlike everything else on the desktop it's backed by a real `FileData` — `Desktop.README_FILE` (`data/files/readme.tres`) — rather than being a hardcoded special case, specifically so it can go through the exact same "any file can be unpacked" path as a `FilesApp` row: `_wire_icon` passes it `_delete_readme` (calls `GameState.delete_readme()` and hides the icon — this part is still readme-specific, not `GameState.delete_file`, since it isn't part of the browsable `data/drive.tres` tree) and `_open_readme_devcrack` (mirrors `FilesApp._open_devcrack` — instantiates `DevCrackApp`, wires `warning_dialog`/`window_manager`/`self_window_id`, calls `.unpack(README_FILE)` — just opened from a desktop icon instead of a file-browser row, tracked under `_singleton_windows["readme_devcrack"]` alongside the existing `"readme"` key for its `NoteViewer` window, the same dual-window split `FilesApp` does with `_open_file_windows`/`_devcrack_windows`). `_open_readme` itself now gates on `GameState.get_lock_reason(README_FILE)` first, branching the warning message the same way `FilesApp._open_file` does — `README_FILE` currently carries no `should_remove` blob (just one flavor blob, `readme_meta`, for a non-empty DevCrack view), so it can never go `PROTECTED`, but it *can* still go `CORRUPTED`: disabling `readme_meta` (the only blob it has) breaks it exactly like disabling essential data on any other file, and the open-attempt will say so (`CORRUPTED`'s "ไฟล์เสียหาย" message). Once past that gate, `_open_readme` opens `NoteViewer` and calls `content.show_plain(README_FILE.content)` — the exact same call `FilesApp._open_file` makes for any other file, no readme-specific viewer method. The warning-header/rule-number/rule-body formatting that used to come from a dedicated `NoteViewer.show_warning_and_rules()` method is now baked directly as BBCode into `readme.tres`'s own `content` field (colors/font hardcoded to match `Palette.ACCENT_WARN`/`TEXT_MAIN`/`TEXT_DIM`/`font_chrome`, since BBCode strings can't call into `Palette`), since `show_plain` already renders with `bbcode_enabled = true`. It is **not** opened automatically at boot anymore, the player must open the icon, and stays hidden across a scene reload if already deleted — see `GameState.is_readme_deleted()` check in `Desktop._ready()`. Current icons: "drive" (`FilesApp` on `data/drive.tres`), "readme.txt" (as above), "trash" (`TrashApp`), "KikuChat" (`KikuChatApp`, see above — opened the same single-instance way as drive/trash, no delete/unpack actions), and "MosMail" (`MosMailApp`, see above — same single-instance pattern, glyph `"@"`). `IconGrid` grew a fourth row for MosMail — its `offset_bottom` was extended from `150` to `195` to fit it without clipping.
